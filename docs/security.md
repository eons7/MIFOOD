# Безопасность МИФУД — что сделано

Документ для защиты проекта. Обычным языком: что защищаем, чем именно
защищаем и как это можно показать комиссии.

## 1. Защита форм от подделки запросов (CSRF)

**Что это.** Атакующий со стороннего сайта мог бы заставить браузер залогиненного
пользователя отправить POST-запрос на МИФУД — например, удалить заказ или
сменить пароль. Защита: каждая форма содержит секретный одноразовый токен,
без которого сервер запрос не примет.

**Чем сделано.** Flask-WTF (`CSRFProtect`). Токен прокидывается во все формы
через `{{ csrf_token() }}`, в HTMX-запросы — через заголовок `X-CSRFToken`
(подкладывается автоматически из `<meta name="csrf-token">` в `base.html`).
Поток SSE (`/sse/*`) исключён через `@csrf.exempt`, потому что это GET-стрим
и токен там не нужен.

## 2. Ограничение частоты запросов (rate limiting)

**Что это.** Защита от перебора паролей, спама регистрации и автоматизированной
накрутки заказов.

**Чем сделано.** Flask-Limiter. Лимиты на ключевых ручках:

| Ручка | Лимит |
| ----- | ----- |
| `POST /auth/login`             | 10 в минуту |
| `POST /auth/register`          | 5 в минуту  |
| `POST /orders/create`          | 30 в минуту |
| `POST /orders/<id>/cancel`     | 20 в минуту |
| `POST /reservations/select-table` | 30 в минуту |
| `POST /reservations/<id>/cancel`  | 20 в минуту |
| `POST /menu/add/<id>`          | 120 в минуту |
| `POST /menu/remove/<id>`       | 120 в минуту |
| `POST /menu/update/<id>`       | 120 в минуту |

После превышения — `429 Too Many Requests`, лимит сбрасывается через минуту.

**Как показать.** В `curl`-цикле сделать 11 POST на `/auth/login` — на
одиннадцатом ответ 429.

## 3. HTTP-заголовки безопасности

**Что это.** Браузерные защиты, включаемые специальными заголовками
ответа: запрет встраивания страницы в `<iframe>`, запрет MIME-снифинга,
правила какой код можно исполнять (CSP), принудительный HTTPS на проде.

**Чем сделано.** Flask-Talisman. Конкретно:

- `Content-Security-Policy: default-src 'self'` — браузер исполняет/загружает
  только ресурсы со своего домена. Все JS/CSS/шрифты/картинки самохостятся.
  Любой `<script src="https://evil.com/x.js">` или injection с внешнего
  домена браузер заблокирует.
- `X-Frame-Options: DENY` — страницу нельзя поместить в чужой iframe
  (защита от clickjacking).
- `X-Content-Type-Options: nosniff` — браузер не «угадывает» тип файла.
- `Referrer-Policy: strict-origin-when-cross-origin` — внешним сайтам не
  утекает полный URL с параметрами.
- `Strict-Transport-Security: max-age=31556926; includeSubDomains` — HSTS,
  браузер год запоминает, что этот домен только по HTTPS.
- На production: `Secure`-флаг для cookie — сессионные куки не уходят
  по голому HTTP.

**Как показать.** DevTools → Network → любой ответ → вкладка Headers, или
`curl -I https://eons7-mifood-d798.twc1.net/auth/login`.

## 4. Безопасное хранение паролей

**Что это.** Пароли никогда не хранятся в открытом виде. В БД лежит только
хеш, а сам пароль восстановить из хеша нельзя.

**Чем сделано.** `werkzeug.security.generate_password_hash` — по умолчанию
использует **PBKDF2 с SHA-256** и солью. При логине вызывается
`check_password_hash`, который сравнивает пароль с хешем за константное
время (защита от timing-атак).

## 5. Политика паролей при регистрации

**Что это.** Не даём пользователю зарегистрироваться с паролем `123` или
`password`. Минимальные требования к надёжности.

**Чем сделано.** Утилита `validate_password()` (`app/utils/security.py`)
проверяет:

- длина не меньше 8 символов;
- хотя бы одна буква (латиница или кириллица);
- хотя бы одна цифра.

При регистрации (`/auth/register`) пароль проходит эту проверку до создания
юзера. При несоответствии — flash-сообщение с конкретной причиной.

## 6. Защита от session fixation

**Что это.** Атакующий мог бы дать жертве свою сессионную куку (например,
через ссылку с `?session=...`), а после логина жертвы получить аккаунт.

**Чем сделано.** При успешном логине вызывается `session.clear()` перед
`login_user(user)`. Старая анонимная сессия (с возможно подсунутыми
данными) полностью отбрасывается, Flask-Login создаёт новую.

## 7. Разделение ролей и контроль доступа

**Что это.** Только администратор может видеть KDS, менять статус заказов,
управлять меню и столами. Студент не должен иметь доступа к админ-ручкам.

**Чем сделано.** Декоратор `@admin_required` (`app/utils/security.py`)
проверяет аутентификацию и роль `is_admin`. Применён ко всем `/admin/*`
маршрутам. Любой не-админ получает `403 Forbidden`.

Студент-уровень: `@login_required` (Flask-Login) на личных ручках
(`/orders/*`, `/reservations/*`, `/menu/*`) + проверка
`obj.user_id == current_user.id` на действиях со своим объектом
(например, `cancel reservation`).

## 8. Аудит действий

**Что это.** В лог сервера пишется кто, откуда и что сделал. Полезно для
расследования инцидентов и просто для понимания, что в системе происходит.

**Чем сделано.** Утилита `audit(action, **fields)` пишет в `app.logger`
строку вида:

```
INFO AUDIT action=order.status_change actor=1 ip=127.0.0.1 order_id=42 old=pending new=confirmed
```

Покрыты события:

- `auth.login_ok` / `auth.login_failed` / `auth.register`
- `order.status_change` (смена статуса заказа админом)
- `order.extend` (продление брони администратором)
- `menu.toggle` (скрытие/возврат блюда)
- `table.toggle` (включение/выключение стола)

## 9. Управление секретами

**Что это.** В коде нет ключей и паролей. Всё конфиденциальное (`SECRET_KEY`,
`DB_PASSWORD`, и т.д.) — в переменных окружения, которые **не попадают в Git**.

**Чем сделано.**

- `.gitignore` исключает `.env`, `instance/`, `*.db`, `__pycache__/`,
  `app/static/uploads/*`.
- В репозитории лежит только `.env.example` — шаблон без реальных значений.
- В production переменные окружения выставлены в панели Timeweb Cloud,
  не в коде.
- Историю Git проверили утилитой **gitleaks** (`gitleaks detect`).
  Результат: `no leaks found`.

## 10. Статический анализ безопасности

**Что это.** Автоматический поиск типовых уязвимостей в Python-коде:
SQL-инъекции, eval, слабая криптография, hardcoded passwords и т.д.

**Чем сделано.** **Bandit** (`bandit -r app/`). Проверка проходит чисто —
**0 issues** уровней Low/Medium/High. Единственные срабатывания (B105,
hardcoded password в `seed.py`) явно помечены `# nosec` — это демо-пароли
для seed-юзеров, а не реальные секреты.

## 11. Автоматическое обновление зависимостей

**Что это.** Уязвимости часто закрываются в библиотеках уже после релиза.
Чтобы не пропустить, нужен бот, который сам открывает PR с обновлением.

**Чем сделано.** Конфигурация **GitHub Dependabot** в
`.github/dependabot.yml`: раз в неделю сканирует `pyproject.toml` и
открывает PR с патчами Python-зависимостей; раз в месяц — для GitHub
Actions.

## 12. Защита за обратным прокси

В production-конфиге включается `ProxyFix` — Flask начинает доверять
заголовкам `X-Forwarded-For`/`X-Forwarded-Proto` от Caddy. Это нужно,
чтобы rate limiter видел реальный IP клиента, а не IP прокси, и чтобы
Talisman корректно определял HTTPS-схему. На dev-конфиге `ProxyFix`
выключен — иначе заголовки можно подделать локально.

## 13. HTTPS и шифрование трафика

**Что это.** Весь трафик между браузером пользователя и сервером
шифруется TLS — никто в сети (Wi-Fi, провайдер) не видит пароли,
сессионные куки и содержимое заказов.

**Чем сделано.** В Timeweb Cloud перед приложением стоит **Caddy** —
обратный прокси с автоматическим Let's Encrypt сертификатом.

- TLS 1.2 + TLS 1.3, современные cipher suites
- Авто-перевыпуск сертификата каждые 60–90 дней (Caddy сам)
- HTTP→HTTPS редирект (Caddy + Talisman `force_https`)
- HTTP/2 и HTTP/3 включены (видно в ответе `alt-svc: h3=":443"`)
- HSTS (см. п. 3)

**Как показать.** Кликнуть 🔒 в адресной строке — «Сертификат действителен,
выпущен Let's Encrypt». Или Mozilla Observatory / SSL Labs:
`https://www.ssllabs.com/ssltest/analyze.html?d=eons7-mifood-d798.twc1.net`.

## 14. Самохостинг внешних ресурсов

**Что это.** Все JS/CSS-библиотеки (Bootstrap, HTMX) положены в репозиторий
(`app/static/vendor/`), а не подгружаются с CDN.

**Зачем:**

- **Безопасность.** CDN может быть взломан или пересобран — наш сайт
  моментально получит подменённый JS. Свои файлы — никаких сюрпризов.
- **Приватность.** CDN видит IP всех посетителей нашего сайта.
- **Доступность.** В РФ часть популярных CDN (`jsdelivr.net`, `unpkg.com`)
  работает нестабильно. Сайт без CDN не зависит от внешней инфраструктуры.
- **CSP проще.** Можно держать строгое `script-src 'self'` без перечисления
  доверенных доменов.

## 15. Файл `.well-known/security.txt`

**Что это.** Стандарт **RFC 9116**. Файл по адресу
`/.well-known/security.txt` сообщает исследователям безопасности, куда
писать о найденных уязвимостях. Используется автоматическими сканерами
(они ожидают этот файл) и просто сигнализирует, что проект серьёзно
относится к безопасности.

**Чем сделано.** Файл лежит в `app/static/.well-known/security.txt`,
отдаётся через роут `/.well-known/security.txt` (`app/__init__.py`).
Содержит контакт для security-репортов.

## Что отложено / не сделано

- **Let's Encrypt сертификат для своего домена** — пока используется
  домен Timeweb (`*.twc1.net`), сертификат на него выпустил Caddy
  автоматически. При подключении своего домена (например, `mifud.ru`)
  Caddy так же выпустит сертификат сам, без ручной настройки.
- **Redis для Flask-Limiter** — сейчас счётчики хранятся в памяти
  процесса. На рестарте контейнера — сбрасываются. Для одного контейнера
  и академического проекта это OK; при масштабировании на N инстансов
  нужен общий Redis (одна строка в конфиге).
- **2FA, CAPTCHA** — для столовой избыточно.
- **Регулярные бэкапы PostgreSQL** — в Timeweb отключены ради экономии,
  включаются галочкой в панели БД.
