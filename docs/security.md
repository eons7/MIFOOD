# Безопасность МИФУД

Документ описывает реализованные в МИФУД меры безопасности с указанием технологий, объёма покрытия и способов проверки. Структурирован по 15 разделам в порядке убывания значимости для защиты приложения.

---

## 1. Защита форм от CSRF

Cross-Site Request Forgery — класс атак, при которых злоумышленник провоцирует браузер аутентифицированного пользователя на отправку запроса от его имени на целевой сайт. Защита реализуется через одноразовый токен в каждой форме, без которого сервер отклоняет запрос.

Реализация: Flask-WTF (`CSRFProtect`). Токен встроен во все формы через `{{ csrf_token() }}`, в HTMX-запросы передаётся через заголовок `X-CSRFToken` (автоматически из `<meta name="csrf-token">` в базовом шаблоне). Поток Server-Sent Events (`/sse/*`) исключён через `@csrf.exempt` как использующий GET-метод.

## 2. Rate limiting

Ограничение частоты запросов защищает от перебора паролей, спама регистрации и автоматизированной накрутки заказов.

Реализация: Flask-Limiter с ограничениями на 9 ключевых маршрутах:

| Маршрут                            | Лимит              |
|------------------------------------|--------------------|
| POST /auth/login                   | 10 в минуту        |
| POST /auth/register                | 5 в минуту         |
| POST /orders/create                | 30 в минуту        |
| POST /orders/&lt;id&gt;/cancel     | 20 в минуту        |
| POST /reservations/select-table    | 30 в минуту        |
| POST /reservations/&lt;id&gt;/cancel | 20 в минуту      |
| POST /menu/add/&lt;id&gt;          | 120 в минуту       |
| POST /menu/remove/&lt;id&gt;       | 120 в минуту       |
| POST /menu/update/&lt;id&gt;       | 120 в минуту       |

При превышении возвращается HTTP 429 Too Many Requests. Лимит автоматически сбрасывается через минуту.

Проверка: 11 последовательных POST на `/auth/login` через curl. На одиннадцатом ответе ожидается код 429.

---

## 3. HTTP-заголовки безопасности

Заголовки ответа задают браузерные ограничения: запрет встраивания страницы в iframe, запрет MIME-снифинга, правила исполнения JavaScript, принудительный HTTPS.

Реализация: Flask-Talisman со следующими настройками.

| Заголовок                       | Назначение                                                              |
|---------------------------------|-------------------------------------------------------------------------|
| Content-Security-Policy         | Разрешён только `self`, без `unsafe-inline` в script-src                |
| X-Frame-Options                 | SAMEORIGIN (защита от clickjacking)                                     |
| X-Content-Type-Options          | nosniff (запрет MIME-снифинга)                                          |
| Referrer-Policy                 | strict-origin-when-cross-origin                                         |
| Strict-Transport-Security       | HSTS на 365 дней с includeSubDomains                                    |
| Cookie Secure flag              | Куки передаются только по HTTPS                                         |

Проверка: DevTools браузера, вкладка Network, заголовки ответа любого маршрута. Альтернативно: `curl -I https://eons7-mifood-d798.twc1.net/auth/login`.

## 4. Хранение паролей

Пароли не хранятся в открытом виде. В базе данных размещается только хэш с солью.

Реализация: `werkzeug.security.generate_password_hash` использует PBKDF2 с SHA-256 и индивидуальную соль для каждого пароля. Проверка пароля при логине выполняется через `check_password_hash`, реализующий константное по времени сравнение для защиты от timing-атак.

---

## 5. Политика паролей при регистрации

Проверка минимальных требований к паролю исключает регистрацию с тривиальными значениями.

Реализация: функция `validate_password()` в `app/utils/security.py` проверяет:

- Длину не менее 8 символов.
- Наличие хотя бы одной буквы (латиница или кириллица).
- Наличие хотя бы одной цифры.

При несоответствии форма регистрации перерисовывается с сохранением имени и email, поля пароля очищаются.

---

## 6. Защита от session fixation

Session fixation — атака, при которой злоумышленник передаёт жертве заранее заданный идентификатор сессии и после логина жертвы получает доступ к её аккаунту через тот же идентификатор.

Реализация: при успешном логине вызывается `session.clear()` перед `login_user(user)`. Старая анонимная сессия полностью отбрасывается, Flask-Login создаёт новую с новым идентификатором.

---

## 7. Разграничение ролей

Только администраторы имеют доступ к панели управления заказами, меню и столами. Студенты ограничены собственными ресурсами.

Реализация: декоратор `@admin_required` в `app/utils/security.py` проверяет аутентификацию и флаг `is_admin`. Применён ко всем маршрутам `/admin/*`. Любой не-административный запрос возвращает HTTP 403.

На уровне студента используется `@login_required` от Flask-Login и явная проверка `obj.user_id == current_user.id` в операциях с собственными объектами.

---

## 8. Аудит-логирование

Действия, имеющие значение для расследования инцидентов, фиксируются в журнале с указанием инициатора, IP и параметров события.

Реализация: утилита `audit(action, **fields)` записывает в `app.logger` структурированную строку.

Пример:

```
INFO AUDIT action=order.status_change actor=1 ip=127.0.0.1 order_id=42 old=pending new=confirmed
```

Покрытые события:

| Событие                  | Назначение                                |
|--------------------------|-------------------------------------------|
| auth.login_ok            | Успешный логин                            |
| auth.login_failed        | Неуспешная попытка логина                 |
| auth.register            | Регистрация нового пользователя           |
| order.status_change      | Изменение статуса заказа администратором   |
| order.extend             | Продление бронирования                    |
| menu.toggle              | Скрытие или возврат позиции меню          |
| table.toggle             | Активация или деактивация стола           |
| payment.succeeded        | Успешная оплата через ЮKassa              |

## 9. Управление секретами

Конфиденциальные параметры (SECRET_KEY, DB_PASSWORD, YOOKASSA_SECRET_KEY) хранятся исключительно в переменных окружения и не попадают в систему контроля версий.

Реализация:

- Файл `.gitignore` исключает `.env`, `instance/`, `*.db`, `__pycache__`, каталог `app/static/uploads`.
- В репозитории присутствует только `.env.example` без реальных значений.
- В production переменные задаются в панели Timeweb Cloud.
- История репозитория проверена утилитой gitleaks с результатом «no leaks found».

## 10. Статический анализ безопасности

Автоматический поиск типовых уязвимостей в Python-коде: SQL-инъекции, использование eval, слабая криптография, hardcoded passwords и подобные паттерны.

Реализация: Bandit (`bandit -r app/`). Результат — 0 issues уровней Low, Medium и High. Срабатывания на B105 (hardcoded password в `seed.py`) помечены `# nosec`, поскольку относятся к демонстрационным паролям seed-пользователей.

---

## 11. Автоматическое обновление зависимостей

Уязвимости в библиотеках устраняются разработчиками после релиза. Своевременное обновление зависимостей критично для безопасности.

Реализация: GitHub Dependabot, конфигурация в `.github/dependabot.yml`. Еженедельное сканирование `pyproject.toml` с автоматическим открытием pull request на обновление Python-зависимостей. Ежемесячное сканирование GitHub Actions.

---

## 12. Работа за обратным прокси

В production-конфигурации активируется ProxyFix — Flask начинает корректно обрабатывать заголовки `X-Forwarded-For` и `X-Forwarded-Proto` от Caddy. Это необходимо для определения реального IP клиента в rate limiter и для корректной работы Talisman с HTTPS-схемой.

В dev-конфигурации ProxyFix отключён во избежание возможности подделки заголовков локально.

---

## 13. HTTPS и шифрование трафика

Весь трафик между браузером пользователя и сервером шифруется по TLS. Перехват пароля, сессионных куков и содержимого заказов в промежуточных сетях исключён.

Реализация: Caddy в Timeweb Cloud с автоматическим выпуском сертификатов Let's Encrypt.

| Характеристика                  | Значение                                  |
|--------------------------------|-------------------------------------------|
| Протокол                       | TLS 1.2 и TLS 1.3                         |
| Шифры                          | Современные cipher suites (cipher modes по умолчанию Caddy) |
| Автоматическое обновление      | Каждые 60–90 дней                         |
| HTTP → HTTPS редирект          | Реализован на уровне Caddy и Talisman     |
| Поддержка HTTP/2 и HTTP/3      | Активна                                   |
| HSTS                           | См. раздел 3                              |

Проверка: иконка замка в адресной строке браузера, инспекция сертификата. Альтернативно: SSL Labs или Mozilla Observatory.

---

## 14. Самохостинг внешних ресурсов

Все JavaScript- и CSS-библиотеки (Bootstrap, HTMX) размещены в репозитории в каталоге `app/static/vendor/`, а не подгружаются с внешних CDN.

Причины:

- Безопасность: компрометация CDN не влияет на приложение.
- Приватность: внешние CDN не получают IP-адреса посетителей.
- Доступность: часть популярных CDN работает нестабильно в РФ.
- Упрощение CSP: достаточно директивы `script-src 'self'` без перечисления доверенных доменов.

## 15. Файл `/.well-known/security.txt`

Стандарт RFC 9116. Файл по адресу `/.well-known/security.txt` сообщает исследователям безопасности контакты для отправки отчётов об уязвимостях. Используется автоматическими сканерами и сигнализирует о готовности проекта к получению security-отчётов.

Реализация: файл размещён в `app/static/.well-known/security.txt`, отдаётся через специальный маршрут в `app/__init__.py`. Содержит контактный email и срок действия (Expires).
