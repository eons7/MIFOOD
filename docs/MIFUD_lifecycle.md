# Жизненный цикл объектов МИФУД

Каждая ключевая сущность системы (Order, Reservation, Cart, MenuItem, User, Payment) описывается конечным автоматом с явно определёнными переходами и условиями их срабатывания. Невалидные переходы между состояниями запрещены на уровне кода.

---

## 1. Order — заказ

### Назначение

Кухонный заказ, содержащий позиции меню, время выдачи, статус приготовления и информацию об оплате.

### Атрибуты

- `id`, `user_id`, `pickup_time`, `created_at`
- `status` — кухонный конечный автомат
- `is_paid` — независимая ось, факт оплаты
- `total_price`, `comment`
- `payment_id` — идентификатор платежа в ЮKassa при инициированной онлайн-оплате

### Конечный автомат

| Из          | В           | Триггер                          | Условие                         |
|-------------|-------------|----------------------------------|---------------------------------|
| —           | pending     | Создание заказа клиентом         | —                               |
| pending     | confirmed   | Подтверждение администратором    | —                               |
| pending     | cancelled   | Отмена администратором или клиентом | —                            |
| confirmed   | ready       | Подтверждение готовности        | —                               |
| confirmed   | cancelled   | Отмена администратором           | —                               |
| ready       | completed   | Выдача заказа                   | При выдаче is_paid становится True  |
| ready       | expired     | Автоматический переход системой   | `now > pickup_time + 15 мин`    |

Терминальные состояния: completed, cancelled, expired. Из них переходы невозможны.

### Источник правды

Словарь `ORDER_TRANSITIONS` в `app/blueprints/admin/routes.py`. Контроллер изменения статуса валидирует переход через этот словарь:

```python
if new_status not in ORDER_TRANSITIONS.get(order.status, []):
    flash('Недопустимый переход статуса', 'danger')
```

### Запрещённые переходы

| Из          | В           | Обоснование                                          |
|-------------|-------------|------------------------------------------------------|
| pending     | ready       | Невозможно пропустить стадию подтверждения           |
| expired     | completed   | Заказ не может быть выдан после истечения окна       |
| completed   | любое       | Терминальное состояние                               |
| cancelled   | любое       | Терминальное состояние                               |

### Ось is_paid

Независимый автомат факта оплаты. Не входит в кухонный FSM.

| Из          | В           | Триггер                                              |
|-------------|-------------|------------------------------------------------------|
| False       | True        | Студент выполняет онлайн-оплату через ЮKassa         |
| False       | True        | Администратор переводит заказ в completed (наличный расчёт) |

### Связь с Reservation

При наличии бронирования заказ и бронь развиваются совместно. Продление бронирования администратором смещает `pickup_time` заказа и `end_time` бронирования на одинаковую величину. Автоматический перевод заказа в expired отменяет связанное бронирование, если оно находится в состоянии scheduled или active.

## 2. Reservation — бронирование стола

### Назначение

Резервирование стола на конкретное время. Создаётся только совместно с заказом.

### Атрибуты

- `id`, `user_id`, `table_id`, `order_id`
- `start_time`, `end_time`
- `status`, `created_at`

### Конечный автомат

| Из          | В           | Триггер                          | Условие                                |
|-------------|-------------|----------------------------------|----------------------------------------|
| —           | scheduled   | Создание                         | —                                      |
| scheduled   | active      | Lazy-переход системой            | `start_time <= now < end_time`         |
| scheduled или active | completed | Lazy-переход системой    | `end_time < now`                       |
| scheduled   | cancelled   | Отмена клиентом или каскад от заказа | —                                  |

### Lazy-переходы

Функции `reservation_service.activate_started()` и `reservation_service.complete_expired()` вызываются на каждый показ списков броней и поиск свободных столов. Состояние броней приводится в актуальное на момент отображения.

Преимущества подхода:

- Отсутствие необходимости в планировщике задач (cron).
- Состояние всегда согласовано с моментом запроса данных.

Ограничение: при отсутствии трафика состояние не обновляется, но это не влияет на корректность работы системы.

### Правило отмены

Отмена бронирования возможна только из состояния scheduled. После start_time клиент уже находится за столом, и отмена нецелесообразна.

```python
def can_cancel(reservation):
    return reservation.status == 'scheduled'
```

## 3. Cart — корзина

### Назначение

Промежуточное состояние между выбором блюд и оформлением заказа. Хранится в серверной сессии, не в базе данных.

### Структура

```python
session['cart'] = {
    "1": 2,    # menu_item_id (str) → quantity (int)
    "5": 1,
}

session['order_draft'] = {
    'cart': {...},
    'pickup_time': '2026-05-03T14:00',
    'comment': 'без лука',
}
```

### Жизненный цикл

| Состояние     | Триггер перехода                                                  |
|---------------|-------------------------------------------------------------------|
| Пустая        | Открытие меню                                                     |
| Заполняется   | Добавление, удаление, изменение количества позиций                 |
| Возвращена в пустую | Удаление всех позиций                                        |
| Черновик заказа | Нажатие кнопки оформления                                       |
| Создан Order  | Подтверждение без бронирования                                     |
| Создан Order + Reservation | Подтверждение с выбором стола                           |
| Сброшена      | Закрытие вкладки браузера                                          |

### Ограничения

- Максимум 10 единиц одной позиции в корзине.
- Максимум 3 активных заказов на одного пользователя.

## 4. MenuItem — позиция меню

### Конечный автомат

| Из          | В           | Триггер                          |
|-------------|-------------|----------------------------------|
| —           | is_available=True | Создание администратором    |
| is_available=True | is_available=False | Toggle администратором |
| is_available=False | is_available=True | Toggle администратором |

### Принцип неудаляемости

Физическое удаление позиций меню не выполняется. Скрытое блюдо не отображается в каталоге и не может быть добавлено в новые заказы, но сохраняется в исторических заказах через внешний ключ `menu_item_id`. Это исключает каскадные ошибки и обеспечивает целостность исторических данных.

### Группировка позиций с размерами

Позиции с суффиксами `_S`, `_M`, `_L` в имени (например, «Капучино_S», «Капучино_M», «Капучино_L») хранятся в БД как отдельные записи. На уровне отображения функция `_group_coffee` в `menu/routes.py` объединяет их в одну карточку с переключателем размеров.

## 5. User — пользователь

### Конечный автомат

| Из          | В           | Триггер                          |
|-------------|-------------|----------------------------------|
| —           | active      | Регистрация                      |
| active      | (без перехода) | —                            |

### Принцип неудаляемости

Удаление пользователей не реализовано на текущей фазе. Поддержка GDPR-совместимого soft delete с анонимизацией персональных данных запланирована в roadmap.

### Роли

Реализована единственная разграничивающая характеристика — флаг `is_admin`. Сложная система ролей и привилегий не применяется ввиду отсутствия необходимости.

## 6. Payment — платёж

### Хранение

Платежи являются объектами ЮKassa. Локально сохраняется только идентификатор платежа в поле `Order.payment_id`.

### Жизненный цикл (упрощённо)

| Этап                                | Сторона          |
|-------------------------------------|------------------|
| POST /orders/<id>/pay               | Клиент           |
| Payment.create в ЮKassa             | Сервер МИФУД     |
| Статус pending на стороне ЮKassa    | ЮKassa           |
| Ввод платёжных реквизитов клиентом   | ЮKassa           |
| Переход в succeeded на стороне ЮKassa | ЮKassa          |
| Отправка webhook на /api/yookassa/webhook | ЮKassa     |
| Re-fetch и валидация                | Сервер МИФУД     |
| UPDATE orders.is_paid = TRUE        | Сервер МИФУД     |

### Идемпотентность обработки webhook

При повторной доставке уведомления выполняется проверка:

```python
if order.is_paid:
    return ('', 200)  # уже обработано
```

Это исключает дублирование операций при повторных отправках webhook со стороны ЮKassa.

## 7. Сводная таблица сущностей

| Сущность     | Хранение                              | Терминальные состояния             | Lazy-FSM                                  |
|--------------|---------------------------------------|------------------------------------|-------------------------------------------|
| Order        | БД                                    | completed, cancelled, expired      | `expire_overdue`                          |
| Reservation  | БД                                    | completed, cancelled                | `activate_started`, `complete_expired`    |
| Cart         | Серверная сессия                      | — (сбрасывается при оформлении)    | —                                         |
| MenuItem     | БД                                    | — (toggle доступности)             | —                                         |
| User         | БД                                    | — (удаление не реализовано)        | —                                         |
| Payment      | ЮKassa (локально `Order.payment_id`) | succeeded, canceled (на стороне ЮKassa) | webhook → re-fetch                    |

### Расположение реализации в коде

- FSM Order: `app/blueprints/admin/routes.py`, словарь `ORDER_TRANSITIONS`.
- Lazy-FSM Reservation: `app/services/reservation_service.py`.
- Автоматический перевод заказа в expired: `app/services/order_service.py`, функция `expire_overdue`.
- Логика продления: `app/services/order_service.py`, функции `extend` и `max_extend_minutes`.
- Проверка конфликта столов: `app/repositories/reservation_repository.py`, функция `has_conflict`.

### Покрытие тестами

Жизненный цикл сущностей покрыт автоматическими тестами в `tests/test_lifecycle.py` (23 теста) и `tests/test_extend_expire.py`. Тесты проверяют все определённые переходы FSM, граничные случаи продления и истечения, конфликты бронирований.
